# @magic-events/db

The data model of magic-events: the Drizzle schema, its migrations and the database client. Every table of every domain
is defined here, in one Postgres database. What each table means is in [docs/data-model.md](../../docs/data-model.md)
and [docs/discovery.md](../../docs/discovery.md).

## Layout

| Path | Holds |
| --- | --- |
| `src/schema/catalogue.ts` | Locations, experiences, their sessions, attribute values, tags, source links and changes |
| `src/schema/discovery.ts` | Sources, runs, listings and raw listings |
| `src/schema/data-processing.ts` | Attributes, their options, tags, seasons, the data warehouse and undefined values |
| `src/schema/organizations.ts` | Tenants |
| `src/schema/identity.ts` | Better Auth's tables: users, sessions, accounts, verifications and API keys |
| `src/schema/events.ts` | The domain event log |
| `src/index.ts` | `createDb(url)`, the `Db` and `Tx` types, and every table |
| `src/migrate.ts` | `ensureDatabase(url)` and `migrateDatabase(url)`, used by the scripts and the tests |
| `src/cli/migrate.ts` | The migrate script: reads the URL from the variable it is given, `DATABASE_URL` by default |
| `src/cli/snapshot.ts` | Saves the development database to `snapshot/hermanus.sql.gz` and restores it |
| `snapshot/hermanus.sql.gz` | The snapshot: a full Hermanus feed that a new checkout starts from |
| `migrations/` | The SQL migrations, generated by drizzle-kit: `0000_married_centennial`, `0001_data_model`, `0002_events_resource_id` and `0003_experience_page_url` |

Each domain owns its tables, and only that domain's repository in `packages/core/src/adapters/storage/` writes them.
Identity's tables are Better Auth's, written through it. A foreign key between domains
points the same way the services call each other: Discovery and Data processing reference Catalogue's location, Data
processing references Discovery's raw listing, and a user references its tenant. Catalogue references nothing outside
itself, so a source link holds a listing's ID with no foreign key.

## Scripts

Run from the repository root, or with `pnpm --filter @magic-events/db <script>`.

| Root script | Does |
| --- | --- |
| `pnpm db:up` | Starts Postgres 18 with pgvector in Docker, on port 5434 |
| `pnpm db:migrate` | Creates the database in `DATABASE_URL` if it is missing and applies the migrations |
| `pnpm db:migrate:test` | The same for `TEST_DATABASE_URL` |
| `pnpm db:generate` | Generates a migration from a change to the schema |
| `pnpm db:restore` | Loads the snapshot into the database in `DATABASE_URL`, when it is empty or missing |
| `pnpm db:snapshot` | Saves the database in `DATABASE_URL` as the snapshot |
| `pnpm db:studio` | Opens Drizzle Studio |
| `pnpm --filter @magic-events/db typecheck` | Checks the types |
| `pnpm --filter @magic-events/db lint` | Runs ESLint |

## The snapshot

`snapshot/hermanus.sql.gz` is the development database as one file: every experience with its sessions, attributes,
tags, embeddings and history, the sources, the listings and the definitions. `pnpm quickstart` at the root starts
Postgres, restores it and seeds, so a new checkout has a full feed with no page to fetch and no model to call.

- **It is a whole dump**, schema and data, with the record of the migrations it has had. `pnpm db:restore` loads it and
  then applies the migrations added since, so the data moves forward as a live database's would.
- **Organisations, users and API keys are left out**, since a key is stored only as a hash. `pnpm db:seed` creates them
  and prints the keys. The job queue's tables are left out too: the server creates them when it starts.
- **`pnpm db:restore` never overwrites.** It stops when the database already has tables. `pnpm db:restore --replace`
  drops the database first.
- **`pg_dump` and `psql` are the container's own**, so they match the server and nothing is installed.

Save a new one with `pnpm db:snapshot` when the data has been improved, and commit the file.

## Changing the schema

1. Edit the table in `src/schema/`.
2. `pnpm db:generate -- --name what_changed`.
3. Read the SQL it wrote in `migrations/`, then `pnpm db:migrate`.

Two things drizzle-kit does not do by itself:

- **Extensions.** `0001_data_model.sql` creates the pgvector extension by hand, before the table that uses it.
- **Adding and dropping columns of one table in one go.** drizzle-kit stops to ask whether a column was renamed, which
  cannot be answered in a script. Generate the drop and the add as two migrations.

A migration that has been applied anywhere is never edited. Add a new one.
