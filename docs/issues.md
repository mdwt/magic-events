# Issues

The working list for version 1, as three tables: what is still being worked on, what is noted for phase 2, and what
is closed. One row per issue. A row says what the issue is and what was decided or built. Where a decision changes how
the system works, it is also in the document that owns the subject.

2026-11-23 · Meiring

**Status:** `In progress` being built now · `To do` decided, and starts when the work it waits on is committed ·
`Open` needs something from outside the code · `Phase 2` noted, and not part of version 1 · `Closed` decided, and
built where it needed building.

## Being worked on

| # | Issue | Area | Status | What is happening |
| --- | --- | --- | --- | --- |
| 45 | A venue whose listing states no coordinates has no position | Data processing | Open | Such an experience is searched from its location's centre. 8 of the 40 captured sources state coordinates (AllEvents.in, Quicket and Webtickets event pages mostly), which gives 138 of 425 captured experiences a position. The other 32 sources give a name or an address only. Geocoding those, through Google behind a port, needs a Google API key in the environment |
| 64 | Nothing says how premium an experience is, so a free parkrun can come before a whale trip | Data processing, Catalogue | In progress | The system is for luxury trips. Decided: a new attribute, `tier`, with one value of luxury, premium, standard or everyday, decided by the classifier from the price, the venue, how many people it is for and how it is described. Search returns the most premium first, and within a tier orders as before: by best match to the query text, or soonest first without one. The 425 captured experiences are being given a tier one by one |
| 61 | A free experience cannot be told from one whose price is not stated | Data processing | In progress | Both have an empty price: 140 of 241 experiences have one, and the rest are what the sources state, or free. Decided: no new field. A price of 0 means free, set only when the listing says so in words, and an empty price means the source states none |
| 62 | The API lists admin operations to a tenant, and the MCP tools are poorly documented | API, MCP | In progress | Decided: REST and MCP are customer-facing only. Both offer search and what changed, and REST also has the health check and the OpenAPI document. The eight onboarding tools come out of MCP, and the tenant, user and credential routes come out of REST with the `tenants.manage` action. A system admin onboards a tenant, adds users and issues and revokes keys through the command line, `pnpm cli:admin`. The whole MCP implementation is under review against the MCP specification and the SDK: the server's instructions, each tool's title and description, a description on every input and output field, annotations and errors |
| 60 | The stored experiences do not carry today's extraction, matching and season fixes yet | Data | To do | They only reach a stored experience when its listing is processed again. One pass, once 61 and 64 are in: `pnpm db:migrate`; `pnpm db:seed`, so the `tier` attribute is defined; then `pnpm cli:captures`, which finds every captured page changed once, because its fingerprint is worked out differently now, and processes each source's pages from its own captures; then `pnpm cli:pipeline -- reprocess --source "<name>"` for each seeded live source and `pnpm cli:pipeline -- process` with `ANTHROPIC_API_KEY` set. Every experience that loses a season tag gets a new version, so changed-since from before the pass reports it as changed. The session running the end-to-end test does it |

## Phase 2

| # | Issue | Area | What is noted |

| 22 | Catalogue never hears that a listing was verified | Discovery | Discovery knows when each listing was last seen. An unchanged listing is not processed, so Catalogue is not told. Stamping last verified on source links is for phase 2 |
| 31 | Pages that only fill in with JavaScript cannot be fetched by the web page adapter | Discovery | Such pages are read with the agent-browser CLI and loaded through the pipeline as captured pages (see [sources.md](sources.md)). A headless browser inside the adapter is for phase 2 |
| 37 | The next source does not take over when the leading listing goes | Data processing | A lower-priority listing only fills empty fields. When the leading link is removed, the experience keeps the values it has. The next source taking over is for phase 2 |
| 40 | A server stopped part way through a fetch uses up that fetch's retries | Jobs | The run stays marked as running until its timeout, and each retry in that time is refused and counted. With the defaults the fetch still happens. Fixing it belongs with the move to more durable jobs in version 2 |
| 42 | Jobs that are given up are only in pg-boss's own table | Jobs | A job whose retries are used up is logged as an error and stays in pg-boss's table. A dead letter queue belongs with the move to more durable jobs in version 2 |
| 50 | A search with a query text waits for the query's embedding | Catalogue | Bedrock takes about 1.3 to 2.0 seconds to embed the query text. After 5 seconds the search ranks by keyword alone. Keeping the embeddings of repeated query texts is for phase 2 |

| 36 | A Quicket event on several dates becomes one long session | Data processing | Fixed. Quicket's search pages give an event only a first and a last moment, so the event gets two sessions, the first day and the last, and the days between are never filled in. | 41 | A failed raw listing can be claimed again before its attempt is counted | Data processing | Fixed. The work runs in a savepoint, so a failure rolls back only the work, and the failed attempt is counted in the same transaction while the claim's lock is still held. | 44 | Nothing runs lint, type checks and tests automatically | Tooling | Built: `.github/workflows/ci.yml` runs lint, the type checks and the tests for every project on every push and pull request, against Postgres with pgvector. It has not run on GitHub yet, because nothing has been pushed |
| 56 | Nothing ever sets the Expected status | Data processing | Built. Extraction sets Expected when a listing gives only a month or a year for an event that recurs and does not say the coming edition is announced. With a day or a recurrence it is Announced, and with tickets on sale Confirmed |
| 54 | The same experience is stored twice when two sources give different months | Data processing | Fixed. When either side is known only to the month or year, dates in the same year, or within three months across a year's end, make a candidate, and matching then decides as before. Day dates on both sides must still overlap, so next year's edition is a different experience. The two duplicates in the development database, the Whale Festival and the solstice Secret Sunset, were merged by hand |
| 57 | A season tag on an experience that is mostly outside the season | Data processing | Fixed. An experience is given a season's tag only when all of its dates fall inside one of the season's periods, so a market that runs all year carries none. In the captured data whale season goes from 189 experiences to 110, and from 72 recurring ones to 2, the two whale watching trips |
| 55 | "Bookable" with nothing to book with | Catalogue | Fixed. An experience is bookable only when it is Confirmed, its booking is Open, and it has a link to book through: its booking link, or failing that its own page address. The flag and the `bookable` filter apply the one rule. The 17 real experiences this was found on are booked by email, phone or RSVP and each has its own page, so they stay bookable once their listings are processed again |
| 58 | A tag filter is not checked against the tag definitions | Catalogue | Fixed. A search's and a changed-since's tags are checked against the tag and season slugs, which Catalogue reads from Data processing. An unknown slug is refused, and the error names the five closest |
| 63 | Two sources of equal priority overwrite each other on every reprocess | Data processing | Fixed. On a tie in priority the listing that was linked to the experience first keeps the lead, and a later one only fills. Reprocessing in any order no longer flips the values or writes a new version. The Whale Festival stays in September, from Xplorio, its first-linked listing |
| 59 | The default radius leaves out towns the sources cover | Catalogue | The default search radius is 60 km, up from 25, so a search of Hermanus reaches Gansbaai, Betty's Bay and Pringle Bay once venues have their own coordinates |
| 46 | A text the embedding model always refuses stays due for ever | Catalogue | Fixed. An experience counts the rounds the model failed on its text and is set aside after `EMBEDDING_MAX_ATTEMPTS`, 3 by default, with one warning. It is tried again when its title or profile changes, and search still returns it, ranked by keyword. When the model fails on everything, a short test text tells an outage from a bad text, and an outage sets nothing aside. Migration 0004. Not covered: a text set aside under one model is not tried again when the embedding model is changed |
| 47 | Changed-since misses an experience whose sessions moved out of the client's dates | Catalogue | Fixed. Changed-since also reports an experience that had a session inside the dates before a change made since the time given, marked `movedOut`, with the sessions it has now. One published after that time, or never in the dates, is not reported. A recurrence changed before this fix is the one case it cannot see |
| 48 | Extraction took a season for an experience, and stored titles that name nothing | Data processing | Fixed. The instructions no longer call a season an experience, an extracted experience whose months are exactly a season's is left out, and a title that is only places, years, months and label words is dropped with a warning. Against the 425 captured titles it drops exactly "Time" and both "Hermanus 2026" |
| 49 | A Wix page's fingerprint changes between fetches | Discovery | Fixed, and the cause was not Wix. A captures load had written its captured pages into the seeded FynArts source, and a captured page's text can never have the fingerprint of the fetched HTML. Captures now load under a source of their own. Two real causes of a changing fingerprint were found on the way and fixed: a web page's fingerprint leaves out the site's frame (its navigation, sidebars and footer, where AllEvents.in rotates lists on every fetch), and a captured page's leaves out its address and read time. All nine seeded web page addresses are stable over two or more fetches. Still true: a source loaded from captures and then fetched by the schedule is processed once more, because the captured text and the fetched HTML differ |
| 51 | Changed-since does not report an experience that changed and then became Past | Catalogue | As designed. An experience that is over is never reported |
| 52 | Changed-since reports cancelled and removed experiences whatever `status` and `bookable` say | Catalogue | As designed. They are what a planner checking back must not miss |
